## 2026-11-28 · 版本号走「后缀区分」：`X.Y.Z-asulada.N`

**背景**：本仓是 `asulada` 的 fork，上游是 `westanke`。并入上游 v2.17.5 之后，树里既有上游
全部内容、又有上游没有的三项（媒体块投影、授权根 realpath 归一、订阅补推轮状态）。若继续顺着
上游 `2.17.x` 往上加（2.17.6、2.17.7…），两条线迟早撞名，而且从版本号既看不出「这是本仓的」，
也看不出「基于上游哪一版」。

**决定**（用户 2026-11-28 拍板「后缀区分」）：版本形如 `X.Y.Z-asulada.N` —— 核心号跟上游
对齐，`-asulada.N` 是本仓在该核心号上的第 N 次发布。

1. `patch|minor|major`：核心号抬位、N 归 1。首个发布是 `2.17.6-asulada.1` —— 核心号取
   「比已并入的上游 2.17.5 高一格」，让步进排序上明确晚于上游那一版。
2. `rev`：核心号不动、N +1（`2.17.6-asulada.1` → `.2`）。同一核心号内的第 N 次发布走这个。
3. 算式从「`package.json` 与最近 tag 取大者」改成**只看 `package.json`**：版本号由一处真值
   确定给出，不再依赖 tag 集合的状态（本仓原先一个 tag 都没有，旧算法的「首个 tag」分支永远命中，
   等于每次都得先解释一遍为什么算出来的不是想要的数）。

**影响**：客户端零影响 —— 能力判断走 `connection.ready` 的能力位，「最低版本」只是安装门槛
（`AGENTS.md` §1）；本仓也不发 npm 包（发布者是上游），没有靠 semver 排序挑版本的消费者。
需要同步改的两处都在机检里：`scripts/bump-release.sh` 的算法，与 `scripts/check-project-docs.ts`
的版本条目正则（原先只认 `X.Y.Z`，带后缀的标题会被判成「缺少该版本条目」—— 那是假红）。

**为什么不用 `2.17.5-asulada.1`**：semver 规定预发布版**小于**同核心号的正式版，那样本仓的
第一个发布在排序上会低于它自己包含的上游 2.17.5，读起来是倒退。

## 2026-11-27 · 助手回复里的媒体由桥投影成结构化块，且投影不碰文件系统

**背景**：模型在回复里写出图片/视频路径（markdown 图片、markdown 链接、正文裸路径）时，手机端
只看到一行字。原因是桥此前逐字节透传内核历史，而客户端侧的 markdown 渲染器没有图片能力、
路径点击又只认 `/` 开头的绝对路径（Windows 的 `D:/…` 被判成相对路径后拼错）。

**决定**：

1. 桥在**出网前**把媒体路径投影成 `{type:'media', mediaType, path, name}`：历史追加进
   `assistant/message` 的 content，实时走 `chat.message.committed` 的独立 `media` 数组
   （committed 帧从不带 content，且 `hasReplyContent` 的判据不能被新增块影响）。能力位
   `media-blocks-v1`。
2. 投影是**纯文本变换，不碰文件系统**：不 `stat`、不探测、不读文件。理由三条 —— 桥的事件泵
   是全局的（一次映射、按订阅者扇出，不知道「谁在看」），在那里 `stat` 等于替所有设备探测任意
   路径，且「存不存在、多大」会随帧发给没有该根授权的设备；映射是同步纯函数，`statSync` 撞上
   慢盘或掉线的网络映射盘会卡住整个事件循环；块里不该出现**只有碰了盘才知道**的信息。
   代价是块里没有 `size`：要大小走 `/roots/resolve`（本来就回 `size`，且过了授权）。
3. 只认绝对路径、只认媒体扩展名白名单、每消息最多 8 块。相对路径不投影 —— 历史里没有任何地方
   记着「这条消息当时的 cwd」，按今天的 cwd 猜会给出一个**看起来能点、点开却是别的文件**的块。
   `reasoning` 块里的路径不算（那是思考草稿）。

**影响**：客户端要做的只剩「按 `mediaType` 选渲染器、按 `path` 走 `roots/resolve` 取字节」；
老客户端把新块当未知块忽略，`HISTORY_FORMAT_VERSION` 不需要升。**这次改动不新增任何读面**：
没有新端点、没有新令牌、不搬字节，能不能取到由既有授权判据说了算（`rootIds` → 会话根最长匹配
→ 双 realpath → `PATH_OUTSIDE_ROOTS`）；块只复述模型自己写出来的路径，不是一次授权。
真正「手机看见」还差客户端一步（`host-Chat` 仓的块 → 视图映射），桥这次只交付协议面与数据。

## 2026-11-27 · 授权根的路径比较一律先 realpath 归一

**背景**：第一次真跑 CI（GitHub Actions 此前被关着）后，macOS 与 Windows 的 fixture 对拍报
「帧形状漂移：workspaces」，实测帧是 `workspaces: []`。根因是授权根入库时（`roots.addRoot`）
解析过符号链接、存的是真实路径，而内核给的 `workspace.path` / `session.cwd` 是它当初用的那个
字符串，未必解析过。纯字符串比较在 macOS（`/var/folders/…` → `/private/var/folders/…`）与
Windows（8.3 短名 `RUNNER~1` → 长名）上整片失配，症状是工作区与会话列表**凭空为空**。

**决定**：新增 `matchRootResolved`（`matchRoot` 的 realpath 归一版），三处比较改用它 ——
`visibleWorkspaces`（改 async）、`sessionRootId`、`listSessions`。解析失败（目录已删、盘已拔出）
退回原串比较：宁可判不可见，也不要让一次 stat 打崩整条列表。

**影响**：纯加性 —— 只会让原本被误判为「根外」的条目重新可见，不会让根外的东西变可见（仍走
最长匹配）。代价是每次列工作区/会话多一轮 realpath syscall（数量级很小，且列表本来就要打内核）。
教训写进 `PITFALLS.md`：**授权根是解析过的路径，凡是拿外部路径去和它比，两边都得先归一**。

**同日追加（第二次 CI 红）**：只做「realpath 失败就退回原串」不够 —— 末段尚不存在时（根内一个
还没建出来的文件）realpath 必然抛 ENOENT，退回原串等于拿未解析的写法去比已解析的根，于是
同一个文件「存在时可见、尚未创建时不可见」。改成解析**最深的已存在祖先**再把尾段拼回去
（`resolveExistingPrefix`），末段不存在不再是失配的理由。同一次也把这两个函数从
`chat-contracts.ts` 挪到 `root-resolver.ts`：加上这段后 chat-contracts 到 619 行，撞了 600 行
预算；而 root-resolver 本来就是「路径落在哪个根内」的家，`chat-contracts.ts` 保留再导出，
`access.ts` / `sessions.ts` 的导入路径不变。
